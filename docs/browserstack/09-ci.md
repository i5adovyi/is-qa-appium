# BS-09 · Run a deliberate cloud test from GitHub Actions

**Stage:** Work with a team · **Time:** 45–75 minutes

## Prerequisites

Write access to your own copy of the repository, permission to configure Actions
secrets, App Automate access and [BS-03](03-first-run.md). If you cannot run
locally, you can still review the pipeline; a first CI attempt needs the same
verified inputs. Reading this lesson does not dispatch a workflow.

This lesson uses the **GitHub repository website**, not the course reader or
BrowserStack dashboard. Your repository must allow Actions, and you need write
access to dispatch its workflow. The manual workflow file must also exist on
the repository's default branch before GitHub exposes manual dispatch; choosing
another branch then selects the revision to run. If **Run workflow** is missing,
check those prerequisites with the repository owner instead of changing secrets
or starting a local test. [GitHub's manual-run guide](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).

## Step by step

1. Save your intended code, inspect `git diff`, commit and push it. Record the
   commit. CI executes the selected remote revision, not unsaved editor buffers
   or an unpushed local commit. Keep `.env` and evidence out of Git.
2. In your repository, open **Settings → Secrets and variables → Actions**.
   Add repository secrets `BROWSERSTACK_USERNAME` and `BROWSERSTACK_ACCESS_KEY`.
   Use the account values; never paste them into workflow YAML. If you cannot
   access settings, ask the repository administrator. See [GitHub secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).
3. Read [browserstack.yml](../../.github/workflows/browserstack.yml). It is
   manually dispatched and requires confirmation `RUN`. The default
   **Learning project checks** workflow checks types, documentation, offline
   labs and reader behavior; it does not use a cloud device.
4. Open **Actions → BrowserStack practice (manual) → Run workflow**. Select the
   intended branch, enter `RUN`, select **login-smoke** for the first attempt,
   and supply the exact Android device/OS supported by your account. The other
   scope, **all-specs**, deliberately includes the full default glob and any
   matching learner specs. Do not select it merely to troubleshoot one case.
   The unchanged Login smoke selection targets one case. Verify the actual
   terminal count, especially if you have added another matching smoke case.
5. Start the workflow only when you intend to use device time. The job checks
   secrets without printing them, installs locked dependencies, audits,
   typechecks, downloads/verifies the APK, performs cloud preflight and runs
   the selected scope. Follow the earliest failing step.
   A red install/audit/typecheck/preflight step is a stop gate. Fix that cause
   and push the fix before a new intentional dispatch; do not remove the gate
   or skip it merely to get a device session.
6. Match the build `training-ci-<run_id>-<run_attempt>` to the provider session.
   Record the GitHub run URL, exact commit, selected scope and executed count.
   A skipped job, such as a confirmation of `NO`, is not a test pass. GitHub's
   expression string comparison is case-insensitive; lowercase `run` also
   satisfies the current guard. Use the displayed `RUN` only when intending
   execution. [Expression rules](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions).
7. On failure, inspect the job log and the `mobile-failures-...` artifact when
   present. It contains available `logs/` files and is retained seven days in
   this workflow. Setup failure may produce no screenshot/XML at all.
8. On cancellation/timeout, check for still-running provider sessions. End only
   your owned sessions using supported controls; record incomplete coverage.

## Reports in CI

The baseline uploads diagnostic artifacts only after failure. Artifact storage
does not automatically parse JUnit or create an Allure page. If you complete
BS-07's optional reporter lab, add a separate upload step for its specific
results directory, usually with `if: always()`, and use a compatible report
viewer/parser if desired. Verify expected cases and preserve the test process's
failure status. Never use `|| true` merely to make report generation run.

Keep uploads narrow and time-limited. Inspect who can access the repository
artifacts before sharing links. Do not broaden workflow permissions, expose
secrets to forked contributions or automatically run account-consuming jobs on
every pull request to bypass an access problem.

## Exercises

### BS-09-A · First manual pipeline

**Task:** predict each job step and its failure meaning, then dispatch one
login-smoke run if authorized access is available. Use a verified device pair.
**Acceptance:** exact commit/run/session correlation, selected and executed
case count, exit/status comparison, and reviewed artifact or explicit absence.
Without access, deliver an annotated workflow and label hosted execution not run.

<details><summary>Hint and review</summary>
The workflow is manual even though ordinary source checks run on push. GitHub's
environment does not inherit your laptop's `.env` or Android emulator.
</details>

### BS-09-B · Green job, no test

**Task:** synthetic evidence: a colleague entered `NO` rather than `RUN`;
GitHub shows a completed workflow with its Android job skipped. Write a status
correction and the next action. Another run stopped during dependency audit;
explain why that is also not a mobile assertion failure.
**Acceptance:** distinguish skipped, setup-blocked and behavior-failed outcomes;
retain the first evidence and avoid claiming zero tests as success.

<details><summary>Hint and review</summary>
Inspect the actual job steps, not just a workflow badge. A new dispatch is an
intentional new attempt. Fix dependency issues separately before cloud execution.
</details>
