# Choose one comfortable study session

You only need one useful task today. Choose it from the table, set a stopping
point and keep the result for your next visit. These routes reuse the course;
they do not add another checklist or change your completion marks.

For the everyday browser, editor and terminal workflow, start with
[How to use this project](how-to-use.md).

**Needed:** a browser or editor for written work; Node 24 and installed project
dependencies for offline coding. Android and BrowserStack are needed only for
the tasks that name them. The hosted reader cannot execute your test files.

## Choose your next task

If you already have an unfinished attempt, resume it before choosing a new topic.
Otherwise use the first row whose starting point matches you.

For the full foundations route use [Start from zero](start-from-zero.md), then
lesson 00 and the device-free parts of 02–03. Use lesson 01's Android setup when
you are ready for lesson 04. Lesson numbers remain useful references; they do
not require you to stop programming while a device download or account is pending.
The [challenge briefing](../challenges/README.md) supplies a separate offline
ticket order. Choose one route at a time; the larger library can wait.

## Match the task to the time you have

The timebox ends a session, not necessarily an exercise. Setup downloads may need
their own session. Keep the last few minutes for saving and a next action.

| Available time | Session shape | Example of enough work |
|---|---|---|
| 20 minutes | 2 recall + 3 read + 10 attempt + 3 inspect + 2 save | C1: predict the examples, run lab 01 once, identify its expected unfinished-starter error |
| 45 minutes | 5 recall + 5 read + 25 attempt + 5 review + 5 save | C2: implement one part of lab 01's contract, run its grader, explain the first remaining mismatch |
| 90 minutes | 5 recall + 10 read + 50 attempt + 15 defect/review + 10 save | Finish one lab attempt, add a discriminating case, observe a controlled defect in a separate scratch copy and restore it |

For a device task, the acceptance criteria still require device evidence.
In a short session you can prepare the initial state and record a prediction;
mark execution pending until the case actually runs. A failed experiment can
be a useful session result when you understand it and save a reproducible next step.

## Return after a break

For targeted practice, choose one ticket in the
[topic assignment bank](../assignments/README.md). L1 gives a guided contract,
L2 asks you to choose and justify an approach, and L3 adds ambiguity or a changed
condition. Use the reader's tool filter to find an offline task while a device
is unavailable. Long tickets can span several sessions; keep a partial handover
under the assignment ID rather than rushing to mark anything complete.

1. Open your latest evidence note and the named exercise. Reading position helps
   you find the page; it does not establish what you can do unaided.
2. Read the previous prediction, command/result and next action. If you have no
   note, choose one small task above; there is no need to reconstruct every visit.
3. Before changing code, inspect `git status --short` and your relevant file.
   Keep existing attempts. Do not reset a starter or reinstall working tools
   simply because you have forgotten a detail.
4. Explain the next action aloud, then run the smallest applicable check when
   its prerequisites are available. Record today's result separately from the old one.
5. End with the [session bookmark](templates.md#session-bookmark-and-partial-handover).
   Write an action such as “predict the two whitespace cases, then run lab 01,”
   rather than “continue TypeScript.”

Keep the bookmark in the current lesson/challenge notes or a private notebook.
Use lesson 00's notes for preparation or F1–F3. Wait for the save confirmation;
export progress before moving between reader addresses. Progress backups contain
notes and marks, not your source files. Save code separately.

## Recall without restarting the whole course

Use one prompt from your actual work; these are suggested intervals, not deadlines.

| When | Small recall task | Evidence and next choice |
|---|---|---|
| Next study day, 2–5 minutes | After lab 01, predict an email with spaces and a password with spaces; after lesson 03, trace the actions with one `await` missing | Explain the outcome before opening your attempt; revisit its smallest unclear part |
| About a week later, 5–10 minutes | Reconstruct one function or assertion in a fresh scratch file, or explain Q01 with a different screen action | Compare with your saved work; record one difference and why it matters |
| After a device investigation | Explain what would happen if its critical action were removed, then rerun that experiment only when the device and restoration plan are ready | Keep prediction separate from observed device evidence; restore the deliberate defect |

Use “needed a hint,” “independent,” and “handled a changed example” as notes
about this attempt. They are more useful than a streak. If recall is difficult,
shrink the task and use one hint. Preserve working learner code during recall;
use a separate file or a written reconstruction.

## Stop with a useful result

Before leaving, save: the exercise ID, what you predicted, what happened, what
remains uncertain and the next smallest action. Include a missing prerequisite
and who or what can resolve it. A completed design can coexist with pending
device execution. Use the [journal's evidence gates](../learning-journal.md#completion-gate)
before marking a lesson complete.
